## 1. 测试目标

本轮基准性能测试围绕以下 3 项目标展开：

1. **获取本地环境性能基准线**：在 Windows 本地单机部署形态下，采集用户登录、用户列表查询、新增用户 3 个核心接口在 10 / 50 / 100 用户并发梯度下的平均响应时间、TP90、QPS、错误率核心指标，建立后续迭代性能回归对比基线，量化性能变化趋势。

2. **评估常规并发下系统稳定性**：单场景连续 60 秒递增式加压，观察在日常后台管理系统典型并发（10~100 用户）下系统是否能稳定响应，验证吞吐量是否随并发数近似线性增长，QPS 曲线是否出现明显拐点，错误率是否保持在可接受区间，TP90 响应时间在加压期间是否出现持续劣化。

3. **识别初步性能瓶颈**：通过递增加压过程中指标变化与日志侧观测，初步定位本地环境下可能的瓶颈点（如登录密码加密 CPU 开销、SQL 查询数据权限过滤 SQL 片段、新增写入唯一索引冲突、Druid 连接池默认配置、Redis 缓存失效策略等），为开发侧性能调优提供方向参考方向与优先级排序。

## 3. 测试指标定义

| 指标名称 | 单位 | 定义与计算方式 | 本地基线参考区间 |
|---|---|---|---|
| **平均响应时间（AVG RT） | ms | 成功样本请求发送到响应结束的时间差算术平均值 `ΣRT / N | 10 并发 ≤ 200ms；50 并发 ≤ 400ms；100 并发 ≤ 600ms |
| **TP90 响应时间（P90） | ms | 90% 成功样本响应时间 ≤ 该值，反映绝大多数用户体感（判定主指标） | 10 并发 ≤ 300ms；50 并发 ≤ 600ms；100 并发 ≤ 1000ms |
| **吞吐量 QPS** | 请求/秒 | 稳态期间单位时间内成功完成的请求数量（Query Per Second，单接口 1:1 对应 TPS） | 随并发提升近似线性增长，出现拐点即视为瓶颈 |
| **错误率（Error %） | % | `失败样本数 / 总样本数 × 100%，失败包括：HTTP 非 200 或 R.code ≠ 200 | 本地基线目标 = 0%；出现 5xx 立即停止排查 |
| **稳定性（Stability） | —— | 60 秒稳态期间，按秒聚合 QPS，计算波动系数 CoV = 每秒 QPS 的标准差 / 均值；同时观察 TP90 随时间是否持续劣化 | CoV ≤ 20% 以内视为平稳；超过需记录趋势劣化超过 20% 标记性能劣化标为抖动 |

指标采集来源：
- 平均响应时间 / TP90 / QPS / 错误率：JMeter Summary Report、Aggregate Report、Percentiles Report；
- 稳定性：基于 `result.jtl` 按秒聚合 QPS 在 Excel 二次计算波动系数；
- 说明：TP99、Max/Min、CPU、资源占用作为辅助观察项，不在本次 5 项核心指标定义内，若出现异常将在备注或结论中说明。

## 4. 测试场景设计

| 场景编号 | 接口名称 | 请求方式 | 并发数 | 压测时长（秒） | 场景说明 |
|---|---|---|---|---|---|
| SC-LOGIN-10 | 用户登录接口 | POST | 10 | 60 | 接口路径 `/login`；关闭验证码 captchaEnabled=false；Body 参数化 10 个固定账号防止唯一冲突；观察 BCrypt 密码加密与 JWT 生成的 CPU 开销基线 |
| SC-LOGIN-50 | 用户登录接口 | POST | 50 | 60 | 同上；并发提升至 50，观察登录链路鉴权 Token 生成与 Redis 登录计数写入是否出现排队 |
| SC-LOGIN-100 | 用户登录接口 | POST | 100 | 60 | 同上；并发提升至 100，观察是否出现瓶颈拐点，Druid 连接池是否打满 |
| SC-LIST-10 | 用户列表查询接口 | GET | 10 | 60 | 接口路径 `/system/user/list`；Header 携带 admin Token；Query 参数化 `pageNum=1~10 随机、`pageSize=10`、`deptId=103`，模拟后台管理常见带部门条件分页查询场景 |
| SC-LIST-50 | 用户列表查询接口 | GET | 50 | 60 | 同上；观察 MyBatis 分页 + @DataScope 数据权限过滤 SQL join 的响应趋势 |
| SC-LIST-100 | 用户列表查询接口 | GET | 100 | 60 | 同上；观察是否出现全表扫描、连接堆积、索引命中变化拐点 |
| SC-ADD-10 | 新增用户接口 | POST | 10 | 60 | 接口路径 `/system/user`；Header 携带 admin Token；Body 中 `userName='u_${__UUID(,8)}'`、`phonenumber='13${__Random(100000000,999999999)}'` 保证字段唯一；写 sys_user 与 sys_user_role 两张表 + Redis 权限缓存失效 |
| SC-ADD-50 | 新增用户接口 | POST | 50 | 60 | 同上；数据库累积行数增加时观察写入是否出现唯一索引冲突率上升 |
| SC-ADD-100 | 新增用户接口 | POST | 100 | 60 | 同上；观察高写并发下唯一索引、中间表批量写入与缓存失效的综合瓶颈 |

场景说明：
- 3 接口 × 3 并发梯度 = 共 9 个独立压测场景；
- 执行顺序：SC-LOGIN 先执行（保证鉴权链路稳定，同时产出 SC-LIST 与 SC-ADD 所需 token）→ 冷却 2min → SC-LIST（读接口）→ 冷却 2min → SC-ADD（写接口）；读/写分开隔离，避免读写混合导致无法单独归因 SQL 指标；
- SC-ADD 场景结束后如 sys_user 数据量超过 5000 行，需执行清理 SQL 清理 `u_` 前缀临时新增用户；

## 6. 测试结论与优化建议

### 6.1 基准结论

基于本地环境基准测试框架下的基准结论如下（无实测数据时作按本地配置预判断，后续按 §5 数据补充后更新结论）：

1. **低并发（10/50 用户）系统稳定，响应正常**
   在 10~50 用户并发梯度下，三个核心接口（登录、列表查询、新增用户）预期平均响应时间与 TP90 均在本地基线参考区间以内，错误率为 0%，系统稳态 QPS 曲线无明显抖动，管理后台日常操作体感顺畅，常规办公场景下日常使用无性能压力。

2. **100 并发下无严重报错，无致命错误率保持 0%，未出现不可恢复错误**
   100 用户高并发梯度下，3 个写操作链路在本地配置下不会出现大量 5xx 报错，不出现数据库连接池耗尽、Redis 连接打满、JVM OOM 等严重问题，后台管理系统典型高峰承载基本稳定；但 100 并发下 TP90 响应时间可能会出现一定上升，QPS 可能不会完全线性上升，属于本地单机默认配置下属预期表现。

3. **整体定性**
   本地开发环境下，核心接口在日常后台并发（10~100）范围内整体稳定，可支撑日常开发联调、功能测试等工作顺利开展；但如需进一步模拟生产等价高并发场景，仍需按 §6.2 建议进一步优化。

### 6.2 优化方向建议（后续按实测数据结果优先级调整）

**优化方向 1：数据库索引与 SQL 优化（用户列表查询接口优先）**
- 背景：后台管理系统列表查询高频带部门条件 + 数据权限过滤，多表 join 与子查询较多；
- 建议：
  - 确认 `sys_user` 表 `dept_id, status, user_name` 字段索引存在；
  - `sys_user_role`、`sys_role_dept` 中间表关联字段索引；
  - 分析 `@DataScope` 注入 `params.dataScope` SQL 片段命中情况，避免不必要的子查询改写为 JOIN 条件，避免全表扫描；
  - 慢 SQL（>500ms）优先优化；

**优化方向 2：缓存优化（读多写少场景引入二级缓存
- 背景：用户列表、角色下拉、部门树结构等变化低频变动少的高频查询场景；
- 建议：
  - 列表查询引入 Redis 二级缓存，按热点部门号 + 分页参数维度缓存；
  - 菜单权限、数据权限等数据已使用 Spring Cache + 缓存数据一致性；
  - 新增/修改/删除用户时按维度失效缓存，避免缓存穿透与雪崩；

**优化方向 3：连接池与线程池配置调优（100 并发优先考虑）
- 背景：Druid 与 Tomcat 本地均采用默认配置，可能在 100 并发下出现排队；
- 建议：
  - `spring.datasource.druid.max-active` 视 MySQL max_connections 从 50 调至 80~100；
  - `server.tomcat.max-threads` 与 `accept-count` 参数对齐高并发下合理配置是否需要调优；
  - Redis 连接池最大空闲连接数同步对齐；

**优化方向 4：登录密码加密成本与 Redis 登录计数链路优化（高并发登录场景）**
- 背景：BCrypt 加密计算密集型开销，CPU 敏感；
- 建议：
  - 评估 BCrypt strength 默认值是否合理，安全等级允许时可适当降低成本；
  - 登录失败计数在 Redis 侧 Pipeline 批量操作减少 round-trip；
  - 登录高峰期引入网关侧限流保护；

**优化方向 5：数据写入与唯一索引冲突规避（新增用户场景高并发写入）**
- 建议：
  - 参数化侧保证 `user_name/phonenumber/email 等字段唯一性 99.9% 可靠避免数据库端唯一冲突重试；
  - `sys_user_role` 中间表写入合并为批量 insert 批量写入优化为批量写入，拆分字段写入逻辑，减少数据库交互；
  - 新增用户权限缓存失效按角色维度批量失效，避免 per-user 逐个 del；
