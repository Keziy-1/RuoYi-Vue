## 1. 测试目标

本方案针对 RuoYi-Vue v3.9.2 核心系统管理接口执行接口层测试，围绕以下三个核心目标展开：

1. **功能正确性验证**：覆盖认证、用户管理、角色管理、菜单管理、部门管理五大模块的全部对外接口，确保请求参数校验、业务逻辑处理、返回数据结构与接口定义完全一致；CRUD 操作后数据库 `sys_user / sys_role / sys_menu / sys_dept / sys_user_role / sys_role_menu / sys_role_dept` 等表的变更符合预期，字段完整性与唯一约束不被破坏。

2. **鉴权有效性验证**：基于 JWT Token 机制验证全链路鉴权闭环，覆盖无 Token、Token 非法、Token 过期、菜单权限不足、数据权限越权等场景，确保未授权请求被 `code=401 / 403` 正确拦截，响应体 `data` 不泄露敏感信息；RBAC 角色与菜单、数据权限的联动与后端 `@PreAuthorize`、`@DataScope` 注解行为一致。

3. **场景串联通顺性验证**：按真实系统管理员日常操作流程组织跨模块多接口串联（登录 → 建部门 → 建角色并分配菜单与数据权限 → 建用户并分配角色 → 新用户登录 → 验证可见菜单与数据范围 → 重置/修改密码 → 退出登录），保证 `deptId / roleId / userId / token` 等参数在链路中动态传递正确，中间表联动写入与缓存失效无脱节。

| 工具 | 版本 | 选型理由与用途 |
|---|---|---|
| **Postman** | v10.x | 主执行工具。优点：① Collection 目录结构可按「模块 → 接口 → 用例（正常/边界/异常）」三层组织；② Pre-request / Tests 脚本支持 Token 自动提取存入环境变量、响应断言、参数化（UUID/Random 函数）；③ Runner 与 Newman 支持一键批量回归；本次 Collection 环境变量含 `{{baseUrl}} / {{token}} / {{deptId}} / {{roleId}} / {{userId}} / {{menuId}} / {{uuid}}`，贯穿串联链路。 |
| **Fiddler Classic** | v5.x | 辅助抓包工具。用途：① 当 Postman 与前端页面对同一接口响应不一致时，抓包对比请求头/请求体差异（如 Content-Type、Token 拼接方式、编码）；② 异常场景下重放请求（Composer）验证 Bug 复现路径；③ 归档每个模块正常成功样本的 `.saz` 会话作为回归基线，开发修复后可快速对照响应字段。 |
| **禅道（ZenTao）** | v18.x | 用例与缺陷管理平台。用途：① 将 Postman 每条断言对应为一条接口用例（标注模块、优先级 P0/P1/P2、所属维度），并建立「用例 ↔ Postman Request Name」双向映射；② Bug 提报时强制附带：接口路径、请求方法、请求头/体原文、响应体原文、数据库影响行、Fiddler .saz 附件，避免口头描述；③ 缺陷状态流转（新建→已解决→已关闭）与 Postman 回归执行对齐，确保每条 Bug 可追溯到断言。 |

协同流程：
1. 以 Knife4j 文档为基准，在 Postman 中按 5 模块创建文件夹；
2. 每新增一个 Request，即刻在禅道中录入对应接口用例，优先级 P0=主流程、P1=核心字段校验、P2=异常/边界；
3. 断言失败样本一律用 Fiddler 抓包重放确认，截图+报文+预期结果一并入禅道 Bug；
4. 修复后用 Postman Runner 选对应模块批量跑，全部通过 → 禅道状态改已关闭。

## 5. 测试策略

### 5.1 单接口测试策略：参数覆盖、边界值、异常值

每个接口按「参数覆盖 → 边界值 → 异常值」三层展开：

**第一层：参数覆盖（正常值 + 必填/选填组合）**
- 每个写接口（POST/PUT/DELETE）：覆盖「全字段给合法值」「仅必填字段」「选填字段缺省」三类；
- 每个查询接口（GET）：覆盖「无参默认分页」「单条件筛选」「多条件组合筛选」「orderByColumn 排序」四类；
- 断言：响应 `code=200`、返回对象字段名与类型匹配 Knife4j 模型、分页 `rows.length ≤ pageSize`、写操作后详情查询字段值一致。

**第二层：边界值**
- 长度边界：`userName` 2~30 字符（1 字符 / 31 字符）、`phonenumber` 固定 11 位（10 位 / 12 位）、`email` 长度 0~50、`roleName` 0~30、`orderNum` 0~999；
- 数值边界：`pageNum=0`、`pageNum=1`、`pageSize=1`、`pageSize=100`、`orderNum=-1`、`orderNum=0`、`orderNum=99999`；
- 状态边界：`status=0启用 / 1停用` 各一次，`visible=0显示 / 1隐藏`，`menuType=M目录 / C菜单 / F按钮`；
- 树形边界：新增部门/菜单时 parentId=0（顶级）、parentId=末级叶子节点、parentId=不存在 ID。

**第三层：异常值**
- 类型错误：数字字段传字符串 `"abc"`、布尔字段传数字、数组字段传对象；
- 正则非法：手机号 `12345678901`、邮箱 `not-an-email`、`roleKey` 含中文；
- 注入关键字：`userName="admin' OR 1=1 --"`、`remark="<script>alert(1)</script>"`；
- 唯一性冲突：POST 时 `userName` / `phonenumber` / `roleName` / 同级 `deptName` 使用已存在值；
- 主键不存在：PUT/DELETE 接口传 `userId=999999`（不存在）。

Postman Tests 断言模板：
```javascript
pm.test("HTTP 200", () => pm.response.to.have.status(200));
pm.test("业务code=200", () => pm.expect(pm.response.json().code).to.eql(200));
pm.test("必填项缺失应返回错误提示", () => {
  const j = pm.response.json();
  pm.expect([400, 500]).to.include(j.code);
  pm.expect(j.msg).to.not.be.empty;
});
```

### 5.2 场景串联策略：按真实业务流关联多接口，动态传递参数

以「系统管理员新入职一名部门员工并配置权限」为核心业务流，串联 5 个模块共 3 条链路，所有跨接口的动态 ID 一律通过 Postman Tests 脚本写入环境变量复用，不允许手工复制粘贴：

**链路 1：组织与权限初始化（admin 视角）**
1. `GET /captchaImage` → 提取 `uuid` 存 `{{uuid}}`、记录 `captchaEnabled`
2. `POST /login`：admin 登录，`body` 带上 `{{uuid}}` 与 code → Tests 提取 `token` 存 `{{token}}`
3. `GET /system/auth/getInfo`：校验返回 admin 用户信息、`permissions` 含 `["*:*:*"]`
4. `POST /system/dept`：在 `parentId=103`（研发部门）下新增「接口测试组」→ Tests 提取返回 `data.deptId` 存 `{{newDeptId}}`
5. `POST /system/role`：新增角色「接口测试主管」，`menuIds=[...]`、`dataScope=2`（自定义）、`deptIds=[{{newDeptId}}]` → 提取 `data.roleId` 存 `{{newRoleId}}`
6. `POST /system/user`：新增用户 `itester_001`，`deptId={{newDeptId}}`，`roleIds=[{{newRoleId}}]` → 提取 `data.userId` 存 `{{newUserId}}`

**链路 2：新用户登录与权限生效（新用户视角）**
1. 新账号 `itester_001` 独立登录 → 存 token 到 `{{token_user}}`（切换环境变量或单独 Header）
2. `GET /system/auth/getRouters`：断言路由仅包含该角色已分配菜单；
3. `GET /system/user/list`：断言返回用户的 `deptId` 全部属于 `{{newDeptId}}`（自定义数据权限生效）；
4. 尝试 `POST /system/role`（未授权写接口）：断言 `code=403`，数据库角色表未新增。

**链路 3：账号生命周期收尾（admin + 用户混合视角）**
1. admin 调用 `PUT /system/user/resetPwd`：重置 `itester_001` 密码
2. `itester_001` 用旧密码登录 → 断言失败；用新密码登录 → 成功；
3. `PUT /system/user/profile/updatePwd`：`itester_001` 自行修改密码；
4. admin 调用 `PUT /system/user/changeStatus`：停用 `itester_001` → 再次用其 token 请求列表 → `code=401` 提示已停用；
5. admin `DELETE /system/user/{{newUserId}}` → `DELETE /system/role/{{newRoleId}}` → `DELETE /system/dept/{{newDeptId}}`；
6. 数据库检查：`sys_user / sys_role / sys_dept` 三表数据删除，`sys_user_role / sys_role_menu / sys_role_dept` 中间表关联行同步删除。

### 5.3 鉴权专项策略：无 Token、Token 过期、Token 非法、权限不足

| 专项子项 | 操作方法 | 预期结果 | 覆盖接口 |
|---|---|---|---|
| **无 Token** | 任意受保护接口（如 `GET /system/user/list`）请求头移除 `Authorization` 字段直接发送 | `HTTP 401` 或 `R.code=401`，`msg` 含「未登录或登录已过期，请重新登录」，`data` 为空或不泄露 | 认证外的全部 5 模块接口各抽 1 条 |
| **Token 过期** | 方式一：提前登录拿到 token → Redis 手动 `del login_tokens:*` 删除该 token 映射 → 重新请求；方式二：间隔 30+ 分钟后重放原请求 | `code=401`，提示「Token 已过期」或「登录状态已失效」 | 用户列表、角色列表、部门列表 3 条核心读接口 |
| **Token 非法** | ① 删除 `Bearer ` 前缀，直接写 JWT 三串；② JWT 第三段签名任意改字符；③ `Bearer ` 后接非 JWT 字符串如 `abcdefg`；④ 空字符串 `Authorization: Bearer ` | 全部场景均 `code=401`，不返回任何业务数据；不抛异常堆栈到响应 | 新增用户、新增角色 2 条写接口 + 用户列表 1 条读 |
| **权限不足** | 使用 `ry/123456`（普通只读角色）账号登录 → ① 调 `POST /system/user` 新增、② 调 `DELETE /system/role/{id}` 删除、③ 调 `PUT /system/role/dataScope` 改数据权限 | 三条均 `code=403`，`msg` 提示「您没有数据的权限，请联系管理员」；三张表写操作均未生效 | 覆盖「新增/修改/删除」写操作各至少 1 条 |

注意：鉴权专项每一条都需并行提交 admin 作为对照组，排除接口本身异常导致误判为「权限生效」。

### 5.4 异常验证策略：重复提交、越权访问、非法参数

**A. 重复提交验证**
- 同一新增请求（POST /system/user，唯一 userName）在 Postman Runner 中设置 2 次迭代，间隔 < 100ms 快速连跑；
- 预期：第 1 次成功 `code=200`，第 2 次返回明确提示「用户名已存在」或「新增用户 'xxx' 失败，该账号已存在」，数据库用户表仅新增 1 条；
- 其他写接口：`POST /system/role`（角色名重名）、`POST /system/dept`（同级部门重名）同等方法验证。

**B. 越权访问验证（含菜单越权 + 数据越权）**
- 菜单越权：详见 §5.3「权限不足」。
- 数据越权：创建「部门 A」用户，分配角色数据范围=本部门；再创建「部门 B」用户；用「部门 A」账号调 `GET /system/user/list?deptId=部门B` → 预期返回空列表或被过滤为 0 条，不返回部门 B 的任何用户详情、不返回 `phonenumber/email` 等字段；
- 行级越权：用户 U1（只能看自己）调 `GET /system/user/{U2_id}` 查看他人详情 → 预期 `code=403` 或 data=null，不泄露 U2 敏感字段。

**C. 非法参数验证**
- JSON 结构非法：手工构造 `{"userName": admin`（少引号/少括号）+ `Content-Type: application/json` 直接 POST → 响应 `code=500` 或 `400`，`msg` 为可读提示，**不允许响应体中出现 Java StackTrace**；
- 参数类型错位：`pageNum="第一页"`、`deptId="人事部"`（不是数字）、`roleIds="1,2"`（字符串不是数组）→ 后端要么报参数绑定错误并提示，要么容错转换但不得抛 500 数据库 SQLSyntax；
- 参数 XSS/注入：`remark="<script>alert(1)</script>"` 提交新增用户 → 入库后查询详情时返回应被转义或原样存储但前端正确转义（不在接口层面执行脚本）；`userName="a' OR '1'='1"` 查询列表 → 返回匹配不到的正常结果，不注入成功不报 SQL 异常。

异常类缺陷统一在禅道打标签「接口-异常」，必填附件：① Fiddler .saz 原始请求响应；② 异常请求 JSON；③ 数据库执行前后 `SELECT COUNT(*)` 对比截图。
